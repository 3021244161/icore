## 1. 版本概述

### 1.1 版本对比

| 维度 | v0.5（当前） | v0.6（目标） |
|------|-------------|-------------|
| 可观测性 | 标准 logging + /health | **Prometheus Metrics + OpenTelemetry Tracing + 结构化日志** |
| Agent 能力 | 无（只有 Task 编排） | **多 Agent 协作（ReAct / Chain-of-Thought / 委派）** |
| 缓存 | 无 | **语义缓存（相似 query 命中）+ Embedding 缓存** |
| 工作流状态 | 内存 | **持久化（PG）+ 断点续跑 + 审计日志** |
| 消息驱动 | 无 | **Kafka / RabbitMQ 触发器 + 事件驱动 DAG** |
| 安全 | 无 | **API Key + JWT 鉴权 + PII 脱敏 + Prompt 注入检测** |
| 检索 | Vector-only ANN | **混合检索（Dense + BM25）+ Reranking** |
| Prompt 管理 | 硬编码 | **模板管理 + 版本化 + A/B 测试** |
| 弹性 | 基础熔断/降级 | **结构化退避 + 死信队列 + Saga 补偿** |
| 部署 | 手动 | **docker-compose 全栈一键启动 + K8s Helm Chart** |
| 对象存储 | 无（结果塞 API 响应体） | **MinIO / S3 适配 + 预签名 URL + 客户端直传** |

### 1.2 核心目标

1. **可观测性三件套：** Metrics / Tracing / Logging 是任何简历上"做过大规模系统"的最低门槛
2. **多 Agent 协作：** 2024-2026 年最火的 AI 工程方向，简历关键词拉满
3. **生产级弹性：** 死信队列、Saga 补偿事务、语义缓存——面试官看到会问"你怎么处理 LLM 调用失败？"——这就是答案
4. **安全基线：** 鉴权 + 注入检测 + 脱敏，体现对 AI 安全问题的工程认知
5. **对象存储：** 工作流产出文件（报表/图表/转码视频）不走 API 响应体，存 MinIO 返回 URL——零拷贝、不超时
6. **一键部署：** `docker-compose up` 把 icore + Milvus + Neo4j + Redis + PG + MinIO 全拉起来，面试演示 30 秒出效果

## 2. 功能增强

### 2.1 可观测性体系（Metrics / Tracing / 结构化日志）

#### 2.1.1 设计动机

当前只有 `logging.info/warning/error` + 一个 `/health` 端点。但真实生产系统需要：
- **实时指标看板：** 每秒请求数、P99 延迟、错误率、模型 token 消耗
- **分布式追踪：** 一次 `/invoke` → DAG 里 5 个节点 → 3 个模型调用 → 2 次 Milvus 检索，每一步耗时能串起来
- **结构化日志导出：** 不再 `print` 到 stdout，而是推送到 ELK / Loki 做全文检索

### 2.2 Agent 智能节点 — DAG 的一等公民

#### 2.2.1 设计哲学

> **icore 的核心永远是确定性工作流。Agent 不替代 DAG，而是 DAG 中一种特殊节点——当某一步无法事先确定怎么做时，交给 Agent 去动态决策。**

类比：DAG 是**流水线**（第 1 步车削 → 第 2 步抛光 → 第 3 步质检），Agent 节点是流水线上那个**需要临场判断的工位**（"这个零件有瑕疵，返工还是报废？"）。

核心约束：

- Agent 节点和普通 Task 节点在 DAG 中地位平等——都有 `node_id`，都接收上游输出、传给下游节点
- Agent 内部调用的"工具"就是**已注册的普通 Task**（通过 `TaskRegistry`），不另起一套工具系统
- Agent 边界受**可配置硬限制**约束（最多迭代 N 次、最多调 M 次工具），保证不会失控
- 没有 Agent 节点的 DAG 就是普通确定性工作流，加了 Agent 节点才有动态决策能力——**渐进式增强**

#### 2.2.2 DAG 集成方式

Agent 节点在 DAG 中和普通 Task 节点地位完全平等：

```python
dag = DAG()

# 确定性步骤
dag.add_node("chunk", task_name="text_chunker")

# Agent 节点：动态决定如何处理
dag.add_node(
    "decide",
    is_agent=True,
    agent_config=AgentConfig(
        mode=AgentMode.REACT,
        goal="分析每个 chunk 内容类型，选择合适策略",
        max_iterations=5,
        max_tool_calls=10,
        available_tasks=["sql_analyzer", "nlp_analyzer", "code_analyzer"],
        output_schema={...},
    ),
)

# 确定性步骤：汇总 agent 结果
dag.add_node("merge", task_name="merge_analysis")

# 和普通节点一样连边
dag.add_edge("chunk", "decide")
dag.add_edge("decide", "merge")
dag.validate()  # agent 节点在 DAG 眼里就是普通节点
```

**关键约束：** `available_tasks` 必须是已注册的普通 Task。Agent 每次"调工具"实质上就是一次 `task_registry.get(name) → task.execute()`——和 DAG 引擎调度普通节点走完全相同的生命周期（validate → prepare → execute → cleanup），享受同样的熔断、重试、超时保护。不另起一套工具系统。

#### 2.2.3 AgentConfig — 可配置的边界参数

```python
@dataclass
class AgentConfig:
    """Agent 节点的配置，直接挂在 DAGNode.agent_config 上。"""

    mode: AgentMode = AgentMode.REACT
    goal: str = ""                           # 要达成的目标（作为 system prompt 传给 LLM）
    max_iterations: int = 10                 # 最大思考-行动轮数
    max_tool_calls: int = 20                 # 最大 Task 调用次数
    available_tasks: list[str] = field(default_factory=list)
    output_schema: dict | None = None        # 最终输出必须符合 JSON Schema
    supervisor_agents: list["AgentConfig"] = field(default_factory=list)
    swarm_max_transfers: int = 5
```

#### 2.2.4 三种模式

三种模式共享同一个执行器，差异仅在内部循环逻辑：

```
┌──────────────────────────────────────┐
│         AgentNodeExecutor            │
│                                      │
│ REACT:   单个 Agent                  │
│   LOOP: plan → act → observe         │
│         → reflect → 继续/FINISH     │
│                                      │
│ SUPERVISOR:  主管 + 子 Agent         │
│   分解 → fork 并行 → join 结果       │
│         → 汇总 → FINISH              │
│                                      │
│ SWARM:  Agent 之间自由转交           │
│   执行 → 判断转给谁                  │
│        → transfer → ... → FINISH    │
└──────────────────────────────────────┘
```

| 模式 | 什么时候用 | 复杂度 |
|------|-----------|--------|
| REACT | 一个 Agent 加几个 Task 就够，不需要分工 | ⭐ |
| SUPERVISOR | 任务天然可拆成并行子任务，汇总出结果 | ⭐⭐ |
| SWARM | 事先不知道需要多少步，开放式探索 | ⭐⭐⭐ |

#### 2.2.5 示例：数据分析 DAG 中嵌入 Agent 决策点

```
DAG: load_csv ──► agent_decide ──► generate_report
                       │
                  (agent 动态决定调哪个 task)
                       ├─► analyze_trend()
                       ├─► detect_anomalies()
                       └─► segment_customers()
```

Agent 内部执行轨迹：

```
Iteration 1:  Think→"先做趋势分析"  Act→analyze_trend()   Observe→"3月有异常峰值"
Iteration 2:  Think→"深入检测异常"  Act→detect_anomalies() Observe→"3/15-20销量飙升300%"
Iteration 3:  Think→"找到异常，可输出"  Act→FINISH
```

### 2.3 LLM 响应缓存（语义缓存）

#### 2.3.1 设计动机

LLM 调用是最贵、最慢的环节。很多请求是语义相似的（"介绍一下 icore"和"icore 是什么"），不需要重新调模型。语义缓存可以在 embedding 空间做去重：

- 命中缓存：< 10ms，零 token 成本
- 未命中：正常调 LLM，结果写入缓存

#### 2.3.2 方案

```python
class SemanticCache:
    """
    两级缓存：
    L1: 精确匹配（Redis key   = md5(prompt)）
    L2: 语义相似（Milvus ANN  = cosine > 0.95 视为命中）
    """

    async def get(self, prompt: str, threshold: float = 0.95):
        # L1: 精确命中
        exact = await self._exact_cache.get(prompt)
        if exact:
            return exact

        # L2: 语义相似
        vector = await self._embed(prompt)
        neighbors = await self._vectorstore.search(
            "semantic_cache", vector, top_k=1
        )
        if neighbors and neighbors[0].metadata.get("score", 0) >= threshold:
            return neighbors[0].metadata["response"]

        return None  # 未命中

    async def set(self, prompt: str, response: str):
        # 双写：L1 + L2
        await self._exact_cache.set(prompt, response)
        vector = await self._embed(prompt)
        await self._vectorstore.insert("semantic_cache", [VectorDocument(
            id=hashlib.sha256(prompt.encode()).hexdigest(),
            vector=vector,
            metadata={"response": response, "score": 1.0},
        )])
```

- [x] `SemanticCache` 实现 L1 + L2 两级缓存

- [x] 支持 TTL 和 LRU 驱逐
- [x] 缓存命中率指标导出到 Prometheus

### 2.4 工作流持久化与断点续跑

#### 2.4.1 设计动机

当前工作流状态全在内存。服务重启意味着所有 in-flight 工作流丢失、没有历史记录可查。
v0.6 需要：

- **审计：** 谁在什么时候调了什么工作流、结果是什么
- **断点续跑：** 5 步 DAG 执行到第 3 步挂了，修好问题后从第 3 步继续，不用从头来
- **查询：** `GET /history?workflow_name=xxx&status=failed&date=2026-08-01`

#### 2.4.2 方案

```sql
-- 新增表（自举到 PostgreSQL）

CREATE TABLE workflow_executions (
    id          UUID PRIMARY KEY,
    task_id     VARCHAR(255) NOT NULL,
    workflow_name VARCHAR(255) NOT NULL,
    params      JSONB,
    status      VARCHAR(50),       -- PENDING / RUNNING / COMPLETED / FAILED
    started_at  TIMESTAMP,
    finished_at TIMESTAMP,
    error       TEXT,
    -- 断点续跑
    checkpoint  JSONB,              -- {completed_nodes: ["embed", "retrieve"], current_wave: 2}
    result      JSONB
);

CREATE TABLE task_executions (
    id          UUID PRIMARY KEY,
    execution_id UUID REFERENCES workflow_executions(id),
    node_id     VARCHAR(255),
    task_name   VARCHAR(255),
    status      VARCHAR(50),
    input       JSONB,
    output      JSONB,
    started_at  TIMESTAMP,
    finished_at TIMESTAMP,
    retry_count INT DEFAULT 0
);
```

- [x] 每次 `/invoke` 自动在 DB 中插入 `workflow_executions` 记录

### 2.5 消息队列集成（Kafka / RabbitMQ）

#### 2.5.1 设计动机

当前工作流只能通过 HTTP 请求触发。真实场景需要多方集成：

- "当 Oracle 数据库有新订单时，自动跑风控工作流"
- "上游系统发了一条 Kafka 消息，icore 消费后跑 DAG，结果写回另一个 Topic"

消息队列 + icore = 事件驱动工作流引擎。

#### 2.5.2 方案

```python
# icore/triggers/kafka_trigger.py

class KafkaWorkflowTrigger:
    """
    订阅 Kafka Topic，当消息到达时自动执行对应工作流。

    config/triggers.yaml:
        triggers:
          - type: kafka
            topic: new_orders
            workflow: fraud_detection
            group_id: icore-fraud-group
    """

    async def start(self):
        consumer = AIOKafkaConsumer(
            self.topic,
            group_id=self.group_id,
            bootstrap_servers=self.brokers,
        )
        await consumer.start()
        async for msg in consumer:
            await self._invoke_workflow(msg.value)
```

- [x] Kafka 触发器（消费 -> 执行工作流 -> offset commit）

### 2.7 混合检索（Dense + Sparse）与 Reranking

#### 2.7.1 设计动机

当前 RAG 只做纯向量检索（ANN）。工程实践中的"完整 RAG"还需要：

- **混合检索：** Dense（语义向量）+ Sparse（BM25 关键词），取各自的 top-K 然后融合
- **Reranking：** 用 Cross-Encoder 对初检结果重排序，大幅提升 chunk 精度

这是 RAG 工程优化中 ROI 最高的两步。

#### 2.7.2 方案

```python
class HybridRetriever:
    """混合检索器：Dense + Sparse → RRF 融合 → Rerank"""

    async def retrieve(
        self, query: str, top_k: int = 10
    ) -> list[VectorDocument]:
        # 1. Dense 检索 (Milvus ANN)
        dense_results = await self.vectorstore.search(...)

        # 2. Sparse 检索 (BM25 / Elasticsearch)
        sparse_results = await self._bm25_search(query, top_k)

        # 3. RRF (Reciprocal Rank Fusion) 融合
        fused = reciprocal_rank_fusion(dense_results, sparse_results)

        # 4. Cross-Encoder Reranking
        reranked = await self._reranker.rerank(query, fused, top_k)

        return reranked
```

### 2.9 对象存储集成 — MinIO / S3

#### 2.9.1 设计动机

当前工作流的输出只有两种形式：**文本**（JSON result）或**流**（SSE）。但实际企业场景中大量结果是文件：

- 生成的数据报表（JSON / CSV / Excel）
- OCR 后的可搜索 PDF
- 视频转码后的 MP4
- 可视化图表 PNG

这些文件不应该塞进 API 响应体（几十 MB 的 base64 会让网关超时），而应该存入对象存储，返回一个**预签名 URL**——调用方拿到 URL 直接从 MinIO/S3 下载，不经过 icore。

另外，多模态工作流（§5-6）处理音频/视频的中间产物也天然需要对象存储暂存。

#### 2.9.2 接口抽象

```python
# icore/objectstore/__init__.py（已实现）

class ObjectRef:
    bucket: str           # s3://bucket/key
    key: str
    size_bytes: int
    content_type: str     # MIME
    metadata: dict

class BaseObjectStore(ABC):
    async def put(bucket, key, data, content_type, metadata) -> ObjectRef
    async def get(bucket, key) -> bytes | None
    async def presigned_get_url(bucket, key, expires_seconds) -> str
    async def presigned_put_url(bucket, key, expires_seconds) -> str   # 客户端直传
    async def list_objects(bucket, prefix, max_keys) -> list[ObjectRef]
    async def delete(bucket, key) -> bool
    async def delete_prefix(bucket, prefix) -> int
    async def bucket_exists(bucket) -> bool
    async def make_bucket(bucket)
    async def health_check() -> bool
```

两个实现：

| 实现 | 说明 |
|------|------|
| `MinIOAdapter` | lazy import `minio` SDK，支持 MinIO / AWS S3 / 任意 S3-compatible 服务 |
| `InMemoryObjectStore` | 纯 Python，测试/演示用 |

#### 2.9.3 集成方式

```
config/objectstore.yaml
        │
        ▼
bootstrap.build_objectstore() → MinIOAdapter 或 InMemoryObjectStore
        │
        ▼
api/main.py: app.state.objectstore
        │
        ▼
invoke 端点 → ctx.set_objectstore(store)
        │
        ▼
Task.execute() 中调用:
    store = ctx.get_objectstore()
    ref = await store.put("reports", "result.json", json_bytes)
    url = await store.presigned_get_url("reports", "result.json")
```


## 3. 工程增强

### 3.1 结构化弹性策略（退避 / 死信队列 / 补偿事务）

#### 3.1.1 退避策略增强

当前只有 `CircuitBreaker` 和 `_retry_async` 的简单指数退避。增强为可配置策略：

```python
from enum import Enum

class BackoffStrategy(str, Enum):
    CONSTANT = "constant"         # retry_delay * attempt
    LINEAR = "linear"             # retry_delay * attempt
    EXPONENTIAL = "exponential"   # retry_delay * 2^attempt
    EXPONENTIAL_JITTER = "exp_jitter"  # + random jitter (±25%)
```

#### 3.1.2 死信队列（Dead Letter Queue）

```python
class DeadLetterQueue:
    """
    当任务重试耗尽后，进入死信队列。

    - 死信队列内任务可手动重放（POST /admin/dql/replay）
    - 死信队列持久化到 PostgreSQL
    - 超出 TTL 后自动归档
    """
```

#### 3.1.3 Saga 补偿事务

长事务工作流（如"订单处理 → 扣库存 → 通知用户"），如果第三步失败，需要用 Saga 模式回滚：

```python
class SagaWorkflow(BaseWorkflow):
    """每个节点都有对应的 compensate 函数。"""

    def define(self):
        self.dag.add_node("reserve_inventory", compensate=release_inventory)
        self.dag.add_node("charge_payment", compensate=refund_payment)
        self.dag.add_node("send_confirmation")  # 无补偿
        # 如果 charge_payment 失败：
        #   1. 执行 charge_payment.compensate (refund)
        #   2. 执行 reserve_inventory.compensate (release)
```
