## 1. 设计动机与边界

### 1.1 动机

当前 iCore v0.6 所有工作流均通过 Python 代码 `define()` 方法构建 DAG。对于简单、
常见的串行/分支工作流，每次都要写代码是一种不必要的开销。Dify、Coze 等平台已
验证了**拖拉拽构建工作流**的效率和低门槛。

### 1.2 边界（不做什么）

| 场景 | 做法 |
|------|------|
| 简单串行流程（LLM→处理→输出） | **可视化拖拽** ✅ |
| 带条件分支的流程 | **可视化拖拽** ✅（条件边 + 标签） |
| 需要 `input_builder` callable 的复杂数据映射 | **代码构建**（可视化只读查看） |
| 需要引入第三方 Python 包的任务 | **代码构建**（可视化标记为"未适配"） |
| 嵌套子工作流 | **可视化引用**（子工作流节点） |
| 用可视化编辑器修改代码构建的工作流 | **不允许**（只读模式，防止覆盖 `input_builder`） |

### 1.3 与现有系统的关系

```
                    iCore v0.6 (现有)                     iCore v0.7 (新增)
              ┌─────────────────────────┐        ┌─────────────────────────┐
  构建方式    │  Python define() 代码    │   +    │  拖拉拽可视化编排          │
  存储位置    │  workflows/examples/*.py │   +    │  config/workflows/*.json │
  注册机制    │  WorkflowRegistry        │  复用  │  同上（JSON → DAG → 注册）│
  执行引擎    │  WorkflowExecutor        │  复用  │  不感知构建方式             │
  Task 发现   │  TaskRegistry            │  复用  │  API 暴露 registry 列表    │
```

**关键点**：执行引擎不感知工作流是怎么构建的。无论是 `define()` 返回的 DAG 还是
从 JSON 反序列化的 DAG，对 Executor 完全透明。

```
                      │  └── .index.json (清单)   │
                      └───────────────────────────┘
```

### 3.2 数据流（可视化构建 → 执行）

```
用户拖拽编排 → 保存 JSON
    ↓
POST /api/wf/visual  →  validate_visual_workflow()
    ↓                                    
写入 config/workflows/{name}.json        
注册到 WorkflowRegistry（懒加载）       
    ↓
POST /invoke {workflow_name: "my_flow"}
    ↓
WorkflowRegistry.get("my_flow")
    ↓
VisualWorkflowLoader: JSON → DAG → BaseWorkflow 实例
    ↓
WorkflowExecutor.run(dag, ctx, params)  ← 与代码构建完全一致的执行路径
```

### 3.3 数据流（代码构建 → 可视化只读）

```
代码 define() 构建 DAG → 注册到 WorkflowRegistry
    ↓
GET /api/workflows  →  列出所有已注册 workflow
    ↓
GET /api/wf/{name}/dag  →  DAG.to_dict() 序列化
    ↓
前端接收 JSON → dagre 自动布局 → React Flow 只读渲染
```

## 4. DAG 序列化方案

### 4.1 现有结构回顾

```python
# icore/engine/dag.py — 现有结构（仅展示相关部分）

class DAGNode(BaseModel):
    node_id: str
    task_name: str
    workflow_name: str          # 子工作流时使用
    is_subworkflow: bool
    input_builder: Optional[InputBuilder]  # ← callable，不可序列化
    model_id: Optional[str]
    retries: int
    timeout: Optional[float]
    metadata: dict[str, Any]    # ← 自由字段，可序列化

class DAGEdge(BaseModel):
    source: str
    target: str
    condition: Optional[EdgeCondition]  # ← callable，不可序列化
    condition_description: str           # ← 文本，可序列化

class DAG:
    _nodes: dict[str, DAGNode]
    _edges: list[DAGEdge]
    # 现有方法: add_node, remove_node, add_edge, remove_edge,
    #           topological_sort, detect_cycle, validate, get_execution_waves...
```

### 4.2 新增序列化方法

```python
class DAG:
    # ===== 新增方法 =====

    def to_dict(self) -> dict:
        """
        将 DAG 序列化为纯数据字典。

        规则：
        - input_builder callable → 跳过（不可序列化）
        - condition callable     → 跳过（不可序列化），保留 condition_description
        - 节点按 node_id 排序保证确定性输出
        - metadata 原样保留

        Returns:
            {
                "nodes": [
                    {
                        "node_id": "n1",
                        "task_name": "summary",
                        "workflow_name": "",
                        "is_subworkflow": false,
                        "model_id": null,
                        "retries": 0,
                        "timeout": null,
                        "metadata": {},
                        "has_input_builder": false   # ← 新增：标记是否有 callable
                    }
                ],
                "edges": [
                    {
                        "source": "n1",
                        "target": "n2",
                        "condition_description": "",
                        "has_condition": false        # ← 新增
                    }
                ]
            }
        """

    @classmethod
    def from_dict(cls, data: dict) -> "DAG":
        """
        从字典重建 DAG。

        规则：
        - 先建所有节点（node_id, task_name, ...），input_builder=None
        - 再建所有边（source, target, ...），condition=None
        - 调用 validate() 保证结构合法
        - 不恢复 callable（可视化构建的 workflow 没有 callable）
        """

    def to_json(self, indent: int = 2) -> str:
        """to_dict() → json.dumps()"""

    @classmethod
    def from_json(cls, json_str: str) -> "DAG":
        """json.loads() → from_dict()"""
```

### 4.3 `has_input_builder` 字段的设计动机

前端渲染代码工作流的 DAG 时，需要知道节点的 `input_builder` 是否存在。
如果存在，该节点标记为"只读 — 含自定义逻辑"，不允许拖拽修改连线（因为
`input_builder` 中可能有硬编码的数据映射）。这个字段在 `to_dict()` 时
动态计算，不在 `DAGNode` 中持久化存储。

### 5.2 字段说明

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `name` | string | ✅ | workflow 唯一标识，对应 WorkflowRegistry key |
| `description` | string | ❌ | 工作流描述 |
| `version` | string | ❌ | 语义化版本号 |
| `built_by` | string | ✅ | `"visual"` 或 `"code"`（由后端判断填充） |
| `nodes[].node_id` | string | ✅ | 节点唯一 ID（建议 "n1", "n2" ... 或 UUID） |
| `nodes[].task_name` | string | ✅ | 对应 TaskRegistry 中的 task 名 |
| `nodes[].label` | string | ❌ | 画布上显示的名称（默认用 task_name） |
| `nodes[].model_id` | string\|null | ❌ | 覆盖全局模型的模型 ID |
| `nodes[].retries` | int | ❌ | 失败重试次数 |
| `nodes[].timeout` | float\|null | ❌ | 节点超时秒数 |
| `nodes[].position` | object | ✅ | 画布坐标 `{x, y}` |
| `nodes[].input_params` | object | ❌ | 简单类型的节点参数（字符串/数字/布尔） |
| `nodes[].metadata` | object | ❌ | 透传元数据 |
| `edges[].source` | string | ✅ | 起始节点 node_id |
| `edges[].target` | string | ✅ | 终止节点 node_id |
| `edges[].condition_description` | string | ❌ | 条件说明（仅条件边有意义） |
| `edges[].label` | string | ❌ | 边上显示的文字标签 |
| `edges[].label_style` | object | ❌ | 标签样式覆盖 `{color, fontSize}` |
| `canvas.viewport` | object | ❌ | 画布视口状态（缩放/平移位置） |

### 5.3 input_params 的设计边界

`input_params` 仅支持**简单类型**：
- 字符串 (`"hello"`)
- 数字 (`42`, `3.14`)
- 布尔 (`true`, `false`)
- 简单数组 (`["a", "b"]`)
- 简单对象 (`{"key": "value"}`)

**不支持**：
- Python callable
- 文件路径引用
- 动态表达式（如 `{{upstream_node.output}}` — 这些由 executor 的 merge 逻辑处理）
- 复杂嵌套结构

如果 task 的 `input_model` 定义了复杂字段（如 `file: UploadFile`），该 task
标记为"未适配"，可视化编辑器只能作为只读节点展示。

## 6. 任务分类与可视化适配判定

### 6.1 Task 元数据扩展

当前 `BaseTask` 类属性为 `name`, `description`, `input_model`, `output_model`。
v0.7 增加可视化相关元数据：

```python
class BaseTask:
    # ---- 现有 ----
    name: ClassVar[str]
    description: ClassVar[str]
    input_model: ClassVar[type[BaseTaskInput]]
    output_model: ClassVar[type[BaseTaskOutput]]

    # ---- v0.7 新增 ----
    visual_category: ClassVar[str] = "uncategorized"
    """可视化侧边栏分类。取值见 6.2 节。"""

    visual_icon: ClassVar[str] = "default"
    """节点图标名（前端 icon 映射）。"""

    visual_supported: ClassVar[bool] = True
    """是否支持可视化配置。
    False 表示该 task 需要 callable input_builder 或复杂参数，
    可视化编辑器只能以只读方式展示。
    """
```

### 6.2 任务分类体系

```python
class VisualCategory:
    TRIGGER   = "trigger"     # 开始/触发节点（蓝色）
    LLM       = "llm"         # LLM 调用（紫色）
    KNOWLEDGE = "knowledge"   # 知识库/检索（靛蓝色）
    DATA      = "data"        # 数据处理/转换（青色）
    LOGIC     = "logic"       # 分支/循环 逻辑控制（橙色）
    CODE      = "code"        # 代码执行（灰色）
    OUTPUT    = "output"      # 输出/结束（绿色）
    SUBFLOW   = "subflow"     # 子工作流（粉色）
    TOOL      = "tool"        # 外部工具/API 调用（琥珀色）
    OTHER     = "other"       # 其他/未分类
```

### 6.3 自动适配判定（后端 API 返回时动态计算）

后端在 `/api/tasks` 返回每个 task 时，自动判定其可视化适配状态：

```python
def assess_visual_compatibility(task_cls: type[BaseTask]) -> dict:
    """
    分析 task 的 input_model 字段，判断可视化编辑器能否配置。
    
    判定规则：
    1. 所有字段类型都是 str/int/float/bool/Optional[...] → compatible ✅
    2. 包含 File/UploadFile/Bytes/callable/自定义类 → incompatible ❌
    3. 包含嵌套 Pydantic model 但字段全简单类型 → compatible ✅
    4. visual_supported = False → 强制 incompatible
    """
```

判定结果在 API 响应中作为 `visual_compatible: bool` 字段返回。

### 6.4 示例：现有 Task 的分类映射

| Task | visual_category | visual_supported | 原因 |
|------|----------------|------------------|------|
| `document_summary` | `llm` | ✅ | input 为 text:string |
| `entity_extraction` | `llm` | ✅ | input 全简单类型 |
| `rag_qa` | `knowledge` | ✅ | input 简单 |
| `svg_draw` | `llm` | ✅ | input 简单 |
| `svg_inspect` | `logic` | ❌ | 含 MediaFile 参数 |
| `svg_fix` | `llm` | ✅ | input 简单 |
| `report_export` | `output` | ✅ | input 简单 |

## 8. 交互设计

### 8.1 节点操作

| 操作 | 触发方式 | 结果 |
|------|---------|------|
| 添加节点 | 从左侧栏拖拽 task → 画布 | 创建节点在释放位置，自动分配 node_id |
| 移动节点 | 鼠标拖拽节点 | 实时移动，释放后更新 position |
| 选中节点 | 单击节点 | 右侧属性面板显示该节点配置 |
| 多选节点 | Shift + 单击 / 框选 | 批量移动/删除 |
| 删除节点 | 选中 → Delete 键 / 右键 → 删除 | 删除节点 + 关联的所有边 |
| 复制节点 | Ctrl+C → Ctrl+V 或 右键 → 复制 | 克隆节点 + 新 node_id，偏移 50px |
| 重命名节点 | 双击 label | 进入编辑模式，回车确认 |
| 禁用节点 | 右键 → 禁用/启用 | 节点变灰，执行时跳过 |

### 8.2 连线操作

| 操作 | 触发方式 | 结果 |
|------|---------|------|
| 创建连线 | 从 output handle 拖拽到 input handle | 创建边，自动避免自环和多对同向 |
| 删除连线 | 选中边 → Delete / 右键 → 删除 | 删除边 |
| 添加条件 | 选中边 → 右侧属性面板编辑 | 设置 condition_description 和 label |
| 修改条件颜色 | 属性面板中选择 | 成功=绿，失败=红，默认=橙 |

### 8.3 连线约束（不同于普通图形编辑器）

- **不能自环**：source != target
- **不能重复边**：同一 source→target 对只能有一条边（如需多条带不同条件，使用 condition_description 区分）
- **不能回环**：DAG 无环约束 —— 添加边后前端即时运行 `detectCycle()`，若成环则拒绝并提示

## 11. 只读模式：代码工作流的可视化

### 11.1 触发条件

当用户在前端打开 `built_by == "code"` 的工作流时：
- 左上角显示 **"只读模式 — 此工作流由代码构建"** 提示条
- 所有节点不可拖拽移动
- 所有连线不可删除/修改
- 属性面板全部字段 `disabled`
- 侧边栏隐藏（不可添加新节点）
- 右键菜单仅保留"查看详情"

### 11.2 自动布局

代码工作流的 DAG 不含 `position` 字段。前端使用 **dagre** 算法自动计算布局：

```typescript
function autoLayout(dagData: DAGData): {nodes: Node[], edges: Edge[]} {
  const g = new dagre.graphlib.Graph();
  g.setGraph({ rankdir: "TB", nodesep: 80, ranksep: 120 });  // 从上到下
  g.setDefaultEdgeLabel(() => ({}));

  for (const node of dagData.nodes) {
    g.setNode(node.node_id, { width: 220, height: 90 });
  }
  for (const edge of dagData.edges) {
    g.setEdge(edge.source, edge.target);
  }

  dagre.layout(g);

  // 将 dagre 计算出的坐标映射回 React Flow nodes
  return {
    nodes: dagData.nodes.map(n => ({
      ...n,
      position: {
        x: g.node(n.node_id).x - 110,  // 居中偏移
        y: g.node(n.node_id).y - 45,
      },
      draggable: false,                // 只读
    })),
    edges: dagData.edges,
  };
}
```

代码工作流中 `has_input_builder == true` 或 `visual_compatible == false` 的节点：

## 12. 自动布局方案

### 12.1 布局算法选择

使用 **dagre** (Sugiyama 框架实现)，横向从上到下分层：

| 参数 | 默认值 | 说明 |
|------|-------|------|
| `rankdir` | `"TB"` (Top→Bottom) | 主方向从上到下 |
| `nodesep` | 80 | 同层节点水平间距 (px) |
| `ranksep` | 120 | 层间垂直间距 (px) |
| `marginx` | 20 | 画布左右边距 |
| `marginy` | 20 | 画布上下边距 |

### 12.2 布局策略

对于代码工作流，执行 `get_execution_waves()` 获取层级分组，再交给 dagre 微调：

```
Wave 0 (start nodes):         [n1]
Wave 1 (parallel):            [n2, n3]
Wave 2:                       [n4]
Wave 3 (terminal):            [n5]

dagre 输出：
    n2      n3
    └── n4 ──┘
         │
         n5
```

条件分支自动在水平方向展开（有货 → 右，无货 → 左）。

```
├── my_order_flow.json           ← 可视化构建的工作流
├── weekly_report.json           ← 可视化构建的工作流
└── ...（代码构建的不在此目录）
```

### 13.2 加载时机

| 构建方式 | 何时加载到 WorkflowRegistry | 加载方式 |
|---------|--------------------------|---------|
| 代码构建 (`.py`) | 服务启动时 `ICORE_WORKFLOW_MODULES` 导入 | `import module` → `@register_workflow` |
| 可视化构建 (`.json`) | 服务启动时扫描 `config/workflows/` + API 保存时热注册 | `JSON → DAG → 动态 BaseWorkflow → registry` |

### 13.3 动态 BaseWorkflow（VisualWorkflow）

为了复用现有执行引擎，可视化工作流在加载时需要包装为一个实现了 `define()` 的
`BaseWorkflow` 实例：

```python
class VisualWorkflow(BaseWorkflow):
    """
    由 JSON 反序列化动态创建的 BaseWorkflow 子类。

    不覆盖 execute()，使用基类默认实现（define() → DAG → executor.run）。
    """

    def __init__(self, name: str, description: str, dag: DAG) -> None:
        self.name = name
        self.description = description
        self._dag = dag

    def define(self) -> DAG:
        return self._dag
```

### 13.4 与代码工作流同名冲突

如果 `config/workflows/my_flow.json` 和某个 `.py` 模块都注册了 `"my_flow"`：

- **优先代码构建**：`WorkflowRegistry` 已存在的 key 不被覆盖
- 日志 warn 级别提示冲突
- 前端列表显示时标注"代码版本优先，可视化版本被遮蔽"

## 14. 实施路径与风险

### 14.1 分步实施

| 阶段 | 内容 | 预计工作量 | 依赖 |
|------|------|----------|------|
| **P0: 后端基础** | DAG 序列化/反序列化 + VisualWorkflow + 存储 | 1-2 天 | 无 |
| **P1: API 层** | `/api/tasks`、`/api/workflows`、CRUD 端点 | 1 天 | P0 |
| **P2: 前端骨架** | React Flow 画布 + 节点拖拽 + 连线 + 基础 UI | 2-3 天 | P1 |
| **P3: 样式与交互** | 自定义节点/边组件、属性面板、颜色体系 | 2 天 | P2 |
| **P4: 只读模式** | dagre 自动布局 + 代码 DAG 可视化 + 未适配标注 | 1 天 | P1 |
| **P5: 运行时状态** | 执行时节点/边状态叠加（可选） | 1 天 | P3 |
| **P6: 撤销/重做** | 操作历史栈 | 0.5 天 | P2 |

**总计：约 8-10 个工作日**

### 14.2 技术风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|-------|------|---------|
| React Flow ESM CDN 兼容性问题 | 低 | 高 | 准备 fallback 方案：内联 bundle 或改用 @reactflow/core 本地构建 |
| dagre 自动布局对大 DAG 性能差（>50节点） | 中 | 低 | 大 DAG 通常代码构建，手动调过位置——提供一个 position hint 字段给代码 DAG |
| visual_compatible 判定误判（把简单 task 标为不兼容） | 中 | 中 | 支持 task 级别显式声明 `visual_supported = True` 覆盖 |
| 可视化工作流无法表达复杂数据流（`input_builder`） | 高 | 中 | 这是设计取舍：不接受复杂度膨胀。复杂场景走代码构建，可视化只读查看 |
| 前端撤销/重做内存占用（大状态快照） | 低 | 低 | 限制历史栈 50 步，或使用 delta 而非全量快照 |

### 14.3 开放问题

1. **input_params 的 downstream 引用**：可视化节点如何引用上游输出？
   - 方案 A：`"{{n1.output.summary}}"` 占位符语法（类似 Dify）
   - 方案 B：不实现，交给 executor 的 auto-merge（当前 v0.6 行为）
   - **建议**：v0.7 先用方案 B，v0.8 再引入占位符

2. **多个 start node**：当前 DAG 允许多个入口节点。可视化是否限制为单入口？
   - **建议**：不限制，但前端在 start node 旁标"入口"标识

3. **条件分支的 else 语义**：一条判断节点分支出两条条件边（true / false），
   executor 如何知道哪条是 else？
   - **建议**：`condition_description = ""` 的边视为默认（else）分支
