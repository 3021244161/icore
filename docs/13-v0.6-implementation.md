## 1. 实施概述

本文档是 v0.6 增强的落地实施记录，对照 [docs/12-v0.6-enhancement.md](12-v0.6-enhancement.md) 的方向性规划，逐一说明每个功能模块的实现位置、测试覆盖与验收状态。

v0.6 在 v0.5 的基础上引入 9 个功能增强与 5 个工程增强，新增 16 个 Python 模块、3 个示例工作流、9 套部署文件，测试基线从 v0.5 的 ~520 个提升至 **1121 passed + 2 skipped**。

## 6. 接线完成状态（2026-08-02 修复）

v0.6 初版存在"模块孤岛化"问题：代码完整、测试齐全，但 7 个模块从未被 API / executor / bootstrap 引用。经 code review 后已全部修复并接入生产路径：

| 模块 | 接线前状态 | 接线后状态 | 验证方式 |
|------|-----------|-----------|----------|
| **auth** | ❌ 完全未接入 | ✅ `create_auth_dependency` 挂到 `/invoke`；`/health`、`/metrics` 免鉴权；`/history` 挂 `history` 权限（admin/developer/viewer）；`/admin/dlq/*` 挂 `admin` 权限（仅 admin） | 无 key -> 401；viewer -> 403；admin -> 通过 |
| **observability** | ❌ 完全未接入 | ✅ `MetricsMiddleware` + `RequestIDMiddleware` 安装；`GET /metrics` 路由注册 | `curl /metrics` 返回 Prometheus 格式 |
| **persistence** | ❌ 完全未接入 | ✅ executor 每节点 `record_task_execution` + 每 wave `save_checkpoint`；`/invoke` `create_execution`/`complete_execution`/`fail_execution`；`GET /history` 端点 | `curl /history` 返回执行记录 |
| **DLQ** | ❌ 完全未接入 | ✅ executor 节点重试耗尽后 `dlq.enqueue`；`GET /admin/dlq/list` + `POST /admin/dlq/replay` 端点 | `curl /admin/dlq/list` 返回条目 |
| **semantic cache** | ❌ 完全未接入 | ✅ `ModelManager.set_semantic_cache()` + `get_adapter()` 用 `CachedModelAdapter` 包装 | `ICORE_CACHE_ENABLED=true` 启用 |
| **security** | ❌ 完全未接入 | ✅ `/invoke` 入口对 `params` 做 `InjectionDetector.detect`，命中返回 400 | 注入输入 -> 400 `PromptInjectionError` |
| **triggers** | ❌ 完全未接入 | ✅ `bootstrap.build_trigger_manager()` + lifespan `start_all()`/`stop_all()` | `ICORE_TRIGGERS_ENABLED=true` 启用 |
| **hot_reload TriggerManager** | ❌ docstring 承诺但无实现 | ✅ `HotReloadCoordinator` 加 `trigger_manager` 引用 + `_reload_triggers` 回调 | triggers.yaml 变化时 stop -> reload -> start |
| **supervisor trace** | 🟡 异常分支不写 trace | ✅ 子 agent 抛异常时也追加 trace 条目（含 `exception_type`） | trace 完整记录所有子 agent |

### 接线架构

```
bootstrap.create_production_app()
    │
    ├── build_observability() ──────────────> MetricsRegistry
    ├── build_auth_dependency() ───────────> FastAPI Depends
    ├── build_persistence_manager() ───────> WorkflowPersistenceManager
    ├── build_dlq() ───────────────────────> DeadLetterQueue
    ├── build_security() ──────────────────> InjectionDetector
    ├── build_trigger_manager() ──────────> TriggerManager
    ├── build_semantic_cache() ────────────> SemanticCache -> ModelManager.set_semantic_cache()
    │
    └── create_app(... all injected ...)
            │
            ├── app.add_middleware(MetricsMiddleware)
            ├── app.add_middleware(RequestIDMiddleware)
            ├── GET /metrics ──> prometheus_response(registry)（免鉴权）
            ├── GET /history ──[history 权限]──> persistence.get_history()
            ├── GET /admin/dlq/list ──[admin 权限]──> dlq.list()
            ├── POST /admin/dlq/replay ──[admin 权限]──> dlq.replay()
            ├── POST /invoke ──[auth dependency]──> ...
            │       ├── injection_detector.detect(workflow_name + params) ──> 400 if injection
            │       ├── persistence.create_execution()
            │       ├── workflow.execute(ctx, params, execution_id=...)
            │       │       └── executor.run(dag, ctx, params, execution_id=...)
            │       │               ├── _record_node() ──> persistence + dlq
            │       │               └── _save_checkpoint() ──> persistence
            │       └── persistence.complete/fail_execution()
            │
            └── lifespan: trigger_manager.start_all() / stop_all()
                          persistence.close() / dlq.close()
```

### 6.6 条件菱形汇合（ICORE-ISSUE-002，zGo 提交）

### 6.9 缺少通用限流原语（ICORE-ISSUE-005，zGo 提交）

zGo 报告：icore 有 `TokenBucket` / `BackpressureCoordinator` / `BaseDistributedLock` 等，但**没有**「按任意键计数、跨实例共享、固定窗口、非阻塞判定」的限流原语——使用方（用户/IP 频控、登录失败限速等配额场景）只能各自实现，形成重复建设与口径漂移。

**能力核查结论**（issue §2 逐项实证）：`TokenBucket` 属另一语义族（进程内 + 平滑速率补充 + **阻塞等待** + 键固化在 `model_id`）；`BackpressureCoordinator` 度量在飞并发而非时间配额；`BaseDistributedLock` 是锁不是计数。三者不可承载「分布式键控配额」。

**新增**（issue §5.1 接口形态严格对齐，置于 `icore/security/rate_limiter.py` 并从 `icore.security` re-export）：

| 组件 | 说明 |
|------|------|
| `RateLimitDecision` | frozen dataclass：`allowed` / `limit` / `used` / `remaining` / `reset_at` / `retry_after`（仅 denied 有值） |
| `BaseRateLimiter` | 抽象接口：`check(key, *, limit, window)` / `peek(key, *, limit)` / `reset(key)` |
| `MemoryRateLimiter` | 单进程后端：check/peek 内部无 await 点、单事件循环内原子；过期窗口惰性替换 + 节流扫描（`cleanup_interval`，默认 60s，0 = 禁用自动）+ 手动 `cleanup()` |
| `RedisRateLimiter` | 跨实例后端：**单条 Lua 脚本原子完成 INCR + 首次 PEXPIRE**（顺带修复无 TTL 遗留键），杜绝「计数键永不过期」泄漏 Redis 内存；client 注入范式复用 `RedisLock`；键前缀默认 `icore:rate_limit:` |
| `create_rate_limiter` | 工厂（`memory` / `redis`；redis_url 缺省取 `settings.concurrency.redis_url`；驱动懒导入） |

**语义边界**（issue §4/§5.2 刻意划清，防业务规则下沉）：

- **非阻塞**：`check()` 拒绝也立即返回（与 `TokenBucket.acquire()` 阻塞语义刻意区分）；需要排队语义的调用方自行 `while not allowed: await sleep(retry_after)`。
- **固定窗口从首次计数起算**（INCR+TTL 语义）：时区对齐的「自然日重置」由调用方处理，原语不含业务数值与时区。
- **被拒也计数**：`used` 可超 `limit`——防拒绝风暴下的免费试探。
- **失败姿态由调用方决定**：Redis 异常直接传播，原语不做静默降级（fail-open 还是 fail-closed 属业务风险取舍）。
- **可观测**：`icore_rate_limit_checks_total`（label = `backend,outcome`；**限流键刻意不进 label**——user_id/ip 高基数会打爆 Prometheus 序列），`peek` 不记指标。
- **共存不替代**：`TokenBucket`（LLM 速率）与 `BackpressureCoordinator`（在飞并发）语义正确，保持原样。

验证结果：`python -m pytest tests -q` -> **1227 passed, 2 skipped**（0 failed；新增 `tests/test_rate_limiter.py` 45 用例：Memory 语义/并发/清理、Redis fake client Lua 参数与只读 peek、工厂、指标增量、接口签名契约）。

### 6.10 熔断失败率口径 + 背压等待队列深度（ICORE-ISSUE-006，zGo 提交）

zGo M4 消费 icore 降级原语时发现两处口径差异（均已在应用层补偿、不阻塞），按「能力同源化」原则提交轻量增强。**两处均为可选能力、完全向后兼容，未修改任何既有行为。**

**差异一：`CircuitBreaker` 新增可选「时间窗失败率」触发口径**

- 现状：仅「连续失败计数」（任一成功清零，达 `failure_threshold` 触发）——低流量时段少量失败持续数秒即熔断，样本不足且对流量波动不稳健。
- 新增三个可选参数（刻意放在既有字段之后，**位置参数顺序不变**）：`failure_rate_threshold: Optional[float] = None`（(0,1]）、`failure_rate_window: float = 30.0`、`min_samples: int = 10`。
- 语义：设置比率阈值后，CLOSED 态触发判定**切换**为「滑动窗口内失败率 **>=** 阈值 且 样本数 >= `min_samples`」（替代连续计数；`failure_threshold` 在比率模式不参与触发）；未设置时既有语义不变（不记录样本，零开销）。
- 实现要点：`_samples: deque[(timestamp, is_failure)]` 记录窗口样本；`_on_success` 同样参与判定（样本凑满 `min_samples` 的瞬间可能是成功调用）；HALF_OPEN 语义两种模式完全一致；`snapshot()` 透出 `window_samples` / `window_failures` / `window_failure_rate`；`CircuitBreakerRegistry` 透传三参数。
- 契约：`tests/test_circuit_breaker.py::TestWindowedFailureRate` 10 用例（阈值触发 / min_samples 保护 / 替代连续计数 / 成功稀释 / 窗口过期 / HALF_OPEN 不变 / 参数校验 / snapshot / 零开销 / Registry 透传）。

**差异二：`BackpressureCoordinator` 补「等待队列深度」指标**

- 现状：`_ComponentLimiter` 只跟踪 `_active`（在途数）；`asyncio.Semaphore` 的等待者对外不可见，调用方无法从 `snapshot()` 推导队列深度（zGo §14.4 降级触发信号是「等待队列深度 > 50 / > 150」）。
- 新增：`_ComponentLimiter.acquire` 等待路径维护 `_waiting`（进入等待 +1，获得许可或超时/取消 -1，`finally` 全覆盖）；`ComponentStatus` 增加 `waiting: int = 0` 字段（默认 0，向后兼容）；`BackpressureSnapshot.to_dict()` 与 `/health` 自动透出。
- 实现要点：等待计数覆盖 acquire 全程——许可可用的快速路径不让出事件循环，瞬时 +1/-1 不可观测，无需区分快慢路径（避免「先查 `locked()` 再 acquire」的竞态）。
- 契约：`tests/test_backpressure.py::TestWaitingQueueDepth` 6 用例（默认 0 / 无等待 / 单等待者 / 多等待者 / 超时归零 / to_dict 透出）。

**边界划分**（与 ISSUE-005 同一原则）：「怎么数」（窗口统计原语、等待者计数）进 icore；「数多少」（30s / 80% / >50 / >300 等阈值与 L1/L2/L3 迁移语义）留业务方。

验证结果：`python -m pytest tests -q` -> **1243 passed, 2 skipped**（0 failed；较上版新增 16 用例：`TestWindowedFailureRate` 10 + `TestWaitingQueueDepth` 6）。
